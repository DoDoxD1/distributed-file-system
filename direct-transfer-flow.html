Distributed file storage · direct transfer architecture

Move file bytes out of the API server

The current upload path forces the API to receive the full file, decode it, chunk it, write replicas, and rebuild the file again on download. The target design keeps the API as the control plane for auth, ownership, validation, and metadata, while the storage bucket becomes the data plane for upload and download.

Current bottleneck: API-side chunking
Target: signed bucket upload and download
Dedup scope: per user
Dedup key: (owner_user_id, sha256, size_bytes)

At a glance

Read this left to right: what happens now, what changes in the future flow, and how user-level dedup prevents the same user from storing identical bytes twice.

Current architecture

  • Client sends full file bytes to the API as payloadBase64.
  • API decodes the file and chunks it inside GatewayService.uploadFile().
  • Download reverses the flow: the API reads chunks, reconstructs the file, and sends it back.

Target architecture

  • Client asks the API for a short-lived signed URL.
  • Client uploads or downloads bytes directly from the object storage bucket.
  • API still owns auth, metadata commit, namespace isolation, and validation.

User-level dedup

  • The same user reuses an existing object when sha256 and size match.
  • Two different users do not share the same physical object.
  • Logical paths and versions point to stored objects through metadata.

Flow view

Switch between the current request path, the direct-transfer path, and the per-user dedup model. Each card shows who owns the step and where the bytes move.

Upload today

The API handles both the control plane and the file bytes. This is why upload cost scales with file size.

1. Client sends full file payload to POST /api/v1/files client
The request carries payloadBase64, logical path, and optional idempotency key.
2. API authenticates and validates request size api
FileController decodes and size-checks the file before calling the service layer.
3. API splits the file into chunks api
GatewayService.uploadFile() computes checksums, chunks the file, and picks replica nodes.
4. API writes each chunk to storage nodes storage
Replica writes happen from the API process to the configured storage backend.
5. API commits manifest after all bytes have passed through it metadata
Control-plane work and data-plane work are coupled in the same request path.

Download today

The API also reconstructs the file on every download, so large reads hit the app server again.

1. Client calls GET /api/v1/files/content client
The request includes logical path and optional version ID.
2. API resolves manifest and chunk list metadata
The manifest points to stored chunks and replica node IDs.
3. API reads chunks and rebuilds the file api
The app verifies chunk checksums and reconstructs the full payload in memory.
4. API returns the file back to the client client
The full file leaves storage, enters the API process, and then leaves the API again.
Why this hurts
API CPU pays for base64, checksum work, and chunking
File bytes cross the app server on every upload and download
Large files increase memory pressure and response time

Upload with direct bucket transfer

The API becomes a gatekeeper instead of a byte relay. It authenticates, plans, signs, verifies, and commits.

1. Client requests an upload session client
Client sends logical path, size, content type, checksum, and optional idempotency key.
2. API validates user, path, size, and dedup candidate api
If the same user already has the same sha256 and size, the API can skip the upload.
3. API returns a signed PUT URL for a staging key bucket
Example staging key: users/{userId}/staging/{sessionId}.
4. Client uploads bytes directly to object storage client
The file never passes through the API process.
5. Client calls complete api
API verifies object existence, size, checksum, and then commits metadata.

Download with direct bucket transfer

The API still checks ownership and version selection, but the bucket serves the actual bytes.

1. Client asks for a download URL client
The request still uses the logical path and optional version ID.
2. API resolves manifest and validates ownership metadata
The API maps the logical file to a stored object owned by that user.
3. API returns a signed GET URL bucket
The URL is short-lived and scoped to a single object key.
4. Client downloads bytes directly from object storage client
The bucket becomes the data plane for reads.
What stays in the API
Authentication, namespace isolation, size limits, and session validation
Signed URL issuance, finalize checks, and metadata commit
Bucket traffic carries the raw file bytes

User-level dedup rules

Same user plus same bytes means one stored object. Different users never share that object.

Dedup identity
(owner_user_id, sha256, size_bytes)

If these three values match, the new file version can point to an existing stored object.

Canonical object key
users/{userId}/objects/sha256/{sha256}

The object key is deterministic per user, so repeated uploads converge to the same physical location.

Finalize path with dedup

The API decides whether to reuse an object or promote the staging upload into a canonical object key.

1. Check for an existing stored object for the same user metadata
Lookup by (owner_user_id, sha256, size_bytes).
2. If found, skip upload or reuse object immediately api
Create a new file version that references the existing object row.
3. If not found, verify the staging upload and promote it bucket
Copy or move users/{userId}/staging/{sessionId} into the canonical object key.
4. Use a unique constraint to stop race duplicates metadata
Even if two requests race, only one row wins. The loser reuses the winner and deletes its staged upload.
What dedup saves
Repeated uploads by the same user do not create a second object
Different paths can still point to one stored object
Cross-user sharing is intentionally blocked

Architecture choices

These diagrams compare the current request path with the three future choices we discussed. The selected path is direct object transfer with user-level dedup because it removes the API from the byte path without pushing chunk orchestration into the client.

Current model · API chunks every file

Current

The same server handles auth, metadata, chunking, checksums, upload writes, and download reconstruction.

Upload
Client Sends full payloadBase64
→
API controller Auth, path validation, size checks
→
Gateway chunker Split file, hash chunks, pick replicas
→
Storage backend Chunk writes from the API process
→
Metadata DB Commit manifest after writes finish
Download
Storage backend Read chunks back
→
Gateway rebuild Reconstruct file and verify checksums
→
API response Return full file through the server again
→
Client Receives reconstructed file
Tradeoff
  • Simple server-owned chunk logic.
  • Every upload and download pays API CPU, memory, and network cost.

Choice A · direct object transfer with user-level dedup

Selected

The API becomes the control plane. The bucket becomes the data plane. Dedup happens per user by checksum and size.

Upload
Client Requests session with sha256 and size
→
API transfer service Auth, dedup lookup, signed URL issue
→
Object storage bucket Client uploads bytes directly to staging or canonical object
→
Metadata DB Store upload session and object reference
Download
Client Asks for a download URL
→
API transfer service Resolve manifest, validate ownership
→
Object storage bucket Serve bytes through signed GET
→
Client Downloads file without API relay
Why it fits this repo
  • Removes the API from the byte path.
  • Keeps auth, namespace isolation, and metadata on the server.
  • Supports per-user dedup with unique (owner_user_id, checksum_sha256, size_bytes).

Choice B · client-side chunking with signed chunk URLs

Alternative

This preserves chunk-oriented storage in the hot path, but it moves chunk creation and retry orchestration into the client.

Upload
Client chunker Split file locally and hash each chunk
→
API chunk planner Issue chunk plan and signed URLs
→
Bucket chunk objects Client uploads many chunk objects directly
→
Metadata DB Commit chunk manifest after every required chunk exists
Download
Metadata DB Return ordered chunk map
→
Client reassembler Fetch chunks and rebuild file locally
→
Bucket chunk objects Serve many object reads per file
Tradeoff
  • Preserves the current chunk model best.
  • Makes the client much more complex for upload, retry, and download assembly.

Choice C · direct upload, then async ingest into chunked storage

Alternative

This keeps direct upload for the user while preserving chunk-based internal storage, but file commit becomes asynchronous.

Upload
Client Upload one full object through signed URL
→
Staging bucket Store raw uploaded object
→
Ingest worker Read staged file, chunk it, and validate it later
→
Internal chunk store Write chunk replicas after background processing
→
Metadata DB Mark version ready only after ingest completes
Download
Metadata DB Expose only completed versions
→
API or bucket path Depends on whether the canonical copy stays full-object or chunk-only
Tradeoff
  • Keeps direct upload and chunk-based internals together.
  • Adds ingest state, background failure handling, and delayed file availability.

Metadata to add

The transfer flow needs two new pieces of state: one table for in-flight sessions and one table for stored user-owned objects.

dfs_upload_sessions

Column Why it exists
session_id Stable handle for upload init, complete, and abort.
owner_user_id Binds the session to one authenticated user.
logical_path Lets finalize create the right manifest entry.
expected_checksum_sha256 Used for dedup lookup and finalize verification.
expected_size_bytes Guards against truncated or oversized uploads.
staging_object_key Where the direct upload lands before promotion.
status, expires_at Lets workers clean up abandoned sessions safely.

dfs_stored_objects

Column Why it exists
object_id Stable reference from file versions or manifests.
owner_user_id Defines the dedup boundary.
checksum_sha256 Primary content identity for that user.
size_bytes Pairs with checksum to tighten the dedup match.
object_key Canonical bucket path for signed download and reuse.
reference_count Deletes the physical object only when no file version still points to it.

Critical constraint: unique (owner_user_id, checksum_sha256, size_bytes).

Implementation slices

This breaks cleanly into steps. Each slice gives you a usable checkpoint instead of one giant migration.

Slice 1 · schema and contracts

  • Add dfs_upload_sessions and dfs_stored_objects.
  • Add DTOs for upload-session init, complete, and download URL.
  • Add the unique constraint for per-user dedup.

Slice 2 · bucket client signing

  • Extend OracleObjectStorageBucketClient for signed PUT and GET.
  • Add object metadata lookup for finalize checks.
  • Add object copy or promote support from staging to canonical key.

Slice 3 · transfer service

  • Create a direct-transfer service for session init, dedup lookup, and finalize.
  • Keep the API as the control plane.
  • Leave the existing chunked endpoints in place during rollout.

Slice 4 · cleanup and rollout

  • Add session expiration cleanup and staged-object cleanup.
  • Add tests for same-user dedup, cross-user isolation, and finalize races.
  • Deprecate base64 upload and download only after the direct path is stable.

The architectural pivot is simple: if the API chunks the file, the file must pass through the API. If the file must not pass through the API, chunking must move out of the request path. This design moves the bytes to the bucket, keeps ownership and metadata in the API, and uses per-user content hashes to prevent repeated storage.
